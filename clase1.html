Clase 1

Redes Virtuales y Virtual Private Cloud (VPC)

Aprende cómo aislar tus recursos lógicos en la nube y cómo diseñar direccionamientos IP flexibles sin depender de hardware físico ni consolas AWS complejas.

1.1 Teoría: El Condominio de la Nube (VPC)

💡 Guía Docente: La Analogía del Condominio (10 min)

Meta: Que entiendan que una VPC no es más que una red privada virtualizada en servidores gigantescos de Amazon.

  • La analogía: Compara la VPC con un condominio privado cerrado.
    • VPC: Todo el terreno del condominio (muro perimetral). Nadie entra a menos que esté invitado.
    • Subredes (Subnets): Los pasajes o condominios internos. Algunos dan a la calle principal (públicos) y otros están al fondo para mayor privacidad (privados).
    • EC2 (Servidores): Las casas dentro de los pasajes.
    • Internet Gateway (IGW): La portería/guardia del condominio. Si no hay portería, nadie puede entrar desde afuera ni salir.
    • Route Table: El mapa que tiene el cartero/guardia para saber por qué calles transitar.
  • Pregunta detonante: "¿Qué pasa si construyo una casa en un condominio sin portero y sin calles pavimentadas? ¿Puedo recibir pizzas de Uber?" (Respuesta: No, porque no hay Internet Gateway ni Route Tables).

En la computación tradicional, configurar una red segura requería comprar racks de routers físicos, firewalls de hardware y tender metros de cable. En la nube, todo esto se hace mediante **software**.

Una **VPC (Virtual Private Cloud)** es tu propia porción aislada de la nube de AWS. Te permite definir un entorno de red lógica donde despliegas tus servidores (EC2) y bases de datos con total control del tráfico.

La Analogía del Condominio

Imagina que compras un terreno grande y pones un gran muro perimetral. Ese terreno es tu VPC. Dentro del terreno, creas pasajes pavimentados (Subredes) y construyes casas (Servidores EC2). Para que las casas puedan pedir correspondencia al exterior, necesitas construir una portería que conecte con la autopista pública (Internet Gateway) y poner letreros con direcciones claras en los pasajes (Tablas de Rutas).

De la clase anterior: Direccionamiento IP en la nube

Vimos en la **Clase 0** que una IP tiene una porción de red (fija) y una porción de host (libre). En AWS, en lugar de usar máscaras largas tipo 255.255.255.0, usamos la notación **CIDR** (ej: `/24` o `/16`), que abrevia cuántos bits están congelados de izquierda a derecha.

1.3 Práctica: Enrutamiento y Conectividad Externa (IGW)

💡 Guía Docente: Dinámica de Ruteo de Paquetes (15 min)

El problema real en AWS: Los alumnos crean subredes públicas y servidores, pero no se pueden conectar por HTTP porque olvidaron asociar el Internet Gateway o configurar la Route Table.

Usa este simulador para mostrarles que la red funciona por capas lógicas:

  • Paso 1: Intenta enviar el paquete tal como viene (por defecto, Subred Privada). Fallará. Explícales que la IP de la máquina es privada y no hay salida al exterior.
  • Paso 2: Cambia a "Subred Pública". Pero ¡ojo! mantén el Internet Gateway desconectado o sin ruta. Envía de nuevo. Fallará de forma distinta.
  • Paso 3: Activa todas las condiciones (Subred Pública, IGW Conectado, Ruta 0.0.0.0/0 activa). Ahora el paquete llegará. ¡Felicidades! Tienen una red pública funcional.

Una subred en una VPC es **privada por defecto**. Para hacerla **pública** (que pueda comunicarse con internet de ida y vuelta), se necesitan tres elementos configurados correctamente. Simúlalos a continuación:

1.4 Laboratorio: Mi propio Servidor Privado Local

💡 Guía Docente: El Laboratorio Local Paso a Paso (15 min)

El truco pedagógico: Como no tenemos AWS, vamos a usar el propio computador del alumno para simular un servidor e IP privada.

  • Indícales que abran la terminal (Mac: Terminal, Windows: PowerShell).
  • Haz que digiten el comando de Python para levantar un servidor web instantáneo.
  • Pídeles que abran el navegador en `http://localhost:8080` para comprobar el servicio. Explícales que `localhost` / `127.0.0.1` es la "IP de loopback" (la máquina hablándose a sí misma, aislada de la red).
  • **Reto grupal final:** Si están en la misma red Wi-Fi del laboratorio (que actúa como una VPC física compartida), haz que busquen su IP privada (ej: con `ipconfig` o `ifconfig`) y se la den a un compañero. El compañero podrá ver su servidor escribiendo `http://[IP-DEL-COMPAÑERO]:8080`. ¡Esto les vuela la cabeza porque demuestra el ruteo privado local!

No necesitas pagar en AWS para entender qué hace un servidor EC2 o cómo se accede a él mediante una IP privada. Vamos a simularlo usando la terminal de tu computador:

Paso 1: Levantar un Servidor Web Instantáneo

Abre la terminal o consola de tu sistema operativo y escribe el siguiente comando para iniciar un servidor web en el puerto `8080`:

Terminal / Consola
$python3 -m http.server 8080
Serving HTTP on 0.0.0.0 port 8080 (http://0.0.0.0:8080/) ... Active connection from 127.0.0.1...

Paso 2: Acceder al Servidor

Abre tu navegador de internet favorito y escribe la siguiente dirección en la barra de direcciones:

http://localhost:8080

Verás una lista de los archivos de tu carpeta local. La IP `127.0.0.1` (o su alias `localhost`) representa a tu propio computador. Es una dirección privada e inaccesible desde el exterior.

Reto Práctico en Parejas (VPC Física)

Busca tu IP local en la red Wi-Fi (escribe ipconfig en Windows o ifconfig en Mac). Suele empezar con 192.168.x.x o 10.x.x.x. Pídele a un compañero que esté conectado al mismo Wi-Fi que entre a tu servidor usando esa IP en su navegador (ej: http://192.168.1.45:8080). ¡Verá tus archivos! Esto demuestra que están en la misma red local (como una subred compartida en AWS).

1.5 Cierre: Metacognición y Autoevaluación

💡 Guía Docente: Cerrando la Clase (10 min)

Usa estas preguntas para consolidar el aprendizaje antes de terminar la sesión. Pide a tres alumnos distintos que respondan y que expliquen en sus palabras **por qué** eligieron esa alternativa:

  • Pregunta 1: Apunta a recordar el número "mágico" de AWS (5 IPs reservadas).
  • Pregunta 2: Enfoque en comprender la diferencia exacta entre subred pública y privada (no es magia, es una ruta en la Route Table).
  • Pregunta 3: Retiene el concepto clave de VPC como aislamiento de red.

1. Si creas una subred en AWS VPC con el rango 10.0.0.0/24, ¿cuántas direcciones IP útiles estarán disponibles para tus servidores EC2?

A
256 direcciones IP
B
254 direcciones IP (se resta red y broadcast)
C
251 direcciones IP (AWS reserva 5 para su infraestructura)
D
16 direcciones IP
Correcto: AWS reserva 5 direcciones IP por cada subred (las primeras cuatro: .0, .1, .2, .3; y la última: .255 en un bloque /24) para tareas internas del sistema, enrutamiento, DNS y broadcast virtual.

2. ¿Qué diferencia fundamental convierte a una subred en "Pública" dentro de una VPC en AWS?

A
Tiene servidores más potentes o instancias EC2 dedicadas.
B
Tiene una ruta en su Route Table que redirige el tráfico 0.0.0.0/0 hacia un Internet Gateway (IGW).
C
No tiene políticas de firewall o Security Groups aplicadas.
D
Utiliza la dirección de red local 127.0.0.1.
Correcto: Una subred es pública únicamente si posee una ruta explícita por defecto (0.0.0.0/0) en su Tabla de Rutas apuntando al Internet Gateway (IGW) de la VPC, permitiendo el ingreso y egreso de tráfico de internet.

3. ¿Cuál es la razón principal de crear una VPC antes de desplegar cualquier aplicación o base de datos en la nube?

A
Hacer que el almacenamiento de archivos sea ilimitado.
B
Para que AWS configure automáticamente todos nuestros servidores web.
C
Para aislar lógicamente nuestros recursos y definir reglas precisas de tráfico y seguridad.
D
Para poder usar una base de datos local 100% gratis.
Correcto: El aislamiento lógico garantiza la seguridad de tus datos. Al definir subredes privadas, proteges servidores críticos (como bases de datos) de accesos no autorizados directos desde el internet público.
