Auto Scaling: Sobreviviendo a un Colapso

Es hora de la verdad. Llevaremos un servidor al límite (100% de CPU) y veremos cómo AWS detecta el problema y clona el servidor automáticamente para salvarnos de la caída.

T.7 Antes de Empezar — Prerequisitos

💡 Guía Docente: Preparación (5 min)

Meta: Asegurarse de que todos los alumnos tengan lo mínimo necesario antes de empezar. Si algún alumno no tiene VPC propia, pueden usar la VPC por defecto que AWS trae de fábrica (toda cuenta la tiene).

  • Tip: Si la clase anterior fue el taller VPC, los alumnos ya tienen todo. Si no, guíalos a usar la VPC default.
  • Tiempo total estimado del taller: 45-60 minutos.

Solo necesitas estas 2 cosas. Haz clic en cada una cuando la confirmes:

  • Sesión iniciada en AWS Academy / Learner Lab
    Tu lab debe estar en estado "verde" (running). Si está rojo, presiona "Start Lab".
  • Estar en el servicio EC2 de la consola
    Escribe EC2 en la barra de búsqueda superior y haz clic en el resultado.
💡 ¿Necesito una VPC, subredes, Key Pair o Security Group?
No te preocupes por nada de eso. Usaremos la VPC por defecto que toda cuenta AWS trae de fábrica (ya tiene subredes públicas listas). El Key Pair y el Security Group los crearemos durante el taller.
📋 Lo que haremos hoy en 4 pasos:
  1. Crear una plantilla de servidor (Launch Template) → La "receta" para clonar.
  2. Crear un Auto Scaling Group → El "vigilante" que monitorea la CPU.
  3. Conectarnos por SSH y estresar la CPU → Simular un ataque de tráfico.
  4. Ver cómo AWS lanza un servidor de rescate solo → ¡La magia!

1 Crear la Plantilla de Servidor (Launch Template)

💡 Guía Docente: Launch Template (10 min)

Explica la analogía: "La Launch Template es como una receta de cocina. Cada vez que AWS necesite crear un servidor nuevo, seguirá exactamente esta receta: mismo sistema operativo, mismo tamaño, misma configuración."

  • Si algún alumno no tiene Key Pair, que lo cree aquí mismo (paso 3 de la tabla).
  • El User Data ya instala stress automáticamente para que no tengan que hacerlo a mano.

Antes de que AWS pueda clonar servidores automáticamente, necesita saber qué clonar. Para eso existe la Launch Template: es la receta exacta de tu servidor.

1

Navegar al servicio EC2

  • En la barra de búsqueda superior de la consola AWS (donde dice "Search"), escribe EC2 y haz clic en el resultado.
  • En el menú lateral izquierdo, busca la sección Instances y haz clic en Launch Templates.
  • Haz clic en el botón naranja Create launch template.
2

Configurar los campos (usa esta tabla exacta)

Campo en AWSQué escribir / seleccionar
Launch template name MiPlantillaRescate
Template version description Servidor para probar auto scaling (opcional)
Application and OS Images (AMI) En la pestaña Quick Start, elige Amazon Linux. Selecciona Amazon Linux 2023 AMI (la que dice "Free tier eligible").
Instance type t2.micro — Dice "Free tier eligible" al lado.
Key pair (login) Selecciona tu llave existente. ¿No tienes? Haz clic en "Create new key pair", nómbrala llave-autoscaling, tipo RSA, formato .pem, y descárgala.
Network settings Haz clic en Create security group. Nombre: SG-AutoScaling. Descripción: SSH para taller. Agrega una regla: Type: SSH, Source: Anywhere.
3

El Toque Especial: User Data (¡NO saltarse!)

Baja hasta el final de la página y haz clic en el triángulo ▶ Advanced details para desplegarlo. Baja hasta el último campo que dice User data y pega este script:

Amazon Linux 2023 #!/bin/bash yum update -y yum install stress -y
⚠️ ¿Tu profesor indicó usar Ubuntu en vez de Amazon Linux? Entonces pega este script en su lugar:
Ubuntu #!/bin/bash apt update -y apt install stress -y

¿Qué hace este script? Cuando AWS encienda un servidor usando esta plantilla, lo primero que hará (antes de que tú te conectes) es instalar automáticamente la herramienta stress que usaremos para saturar la CPU.

4

Crear la plantilla

Haz clic en el botón naranja Create launch template que está abajo del todo.

✅ Si todo salió bien: Verás un mensaje verde que dice "Successfully created launch template: MiPlantillaRescate". Además, abajo verás una sección de "Siguientes pasos".

👉 Haz clic directamente en el link azul "Crear grupo de Auto Scaling" que aparece en esa pantalla. Eso te lleva directo al siguiente paso sin tener que buscar en el menú.

2 Crear el Auto Scaling Group (El Vigilante)

💡 Guía Docente: ASG (15 min)

Analogía: "El Auto Scaling Group es como un guardia de seguridad que vigila el termómetro de la CPU. Si ve que sube de 50°, llama refuerzos (clona servidores). Si baja, manda a los refuerzos a casa."

  • El wizard tiene 7 pantallas. La mayoría se saltan con Next. La pantalla 4 (Group size) es la única crítica.
  • Recuerda: el ASG creará automáticamente 1 instancia EC2 al terminar. Eso es normal y esperado.

Ahora crearemos el vigilante que usará nuestra plantilla para clonar servidores cuando detecte problemas de CPU. El wizard tiene varias pantallas, pero la mayoría se saltan.

1

Pantalla 1 — Nombre y Plantilla

  • ¿Vienes de la pantalla de éxito del Launch Template? Haz clic en el link "Crear grupo de Auto Scaling" que aparecía ahí.
  • ¿Ya cerraste esa pantalla? No pasa nada: en el menú izquierdo de EC2, baja hasta el final y busca Auto Scaling Groups (está bajo la sección "Auto Scaling"). Haz clic en el botón naranja Create Auto Scaling group.

Haz clic en Next.

⏳ Espera importante: Antes de pasar al siguiente paso, espera a que la instancia esté en estado "Running" (con un círculo verde). Esto toma 1-2 minutos. Puedes refrescar la lista de instancias con el botón de recarga (🔄) en la esquina superior derecha.

3 Llevar el Servidor al 100% de CPU (Modo Caos 💥)

💡 Guía Docente: Estrés (10 min)

Recomendación: Usa EC2 Instance Connect porque no requiere PuTTY ni configuración. Es un clic desde la consola de AWS. Si algún alumno tiene problemas de conexión, verifica que el Security Group tenga el puerto 22 abierto y que la instancia tenga IP pública.

  • El stress puede tardar 1-2 minutos en instalarse vía User Data. Si el alumno se conecta muy rápido y stress no existe, que ejecute sudo yum install stress -y manualmente.

Ahora viene la parte divertida: vamos a conectarnos al servidor que creó el Auto Scaling y vamos a hacerlo sufrir para provocar que se active el escalado.

1

Encontrar tu instancia

  • Ve a EC2 → Instances (menú izquierdo).
  • Busca la instancia que dice "Running" con un círculo verde. Es la que creó el Auto Scaling Group (no tendrá nombre, o tendrá un nombre genérico).
  • Selecciónala haciendo clic en su checkbox.
2

Conectarse por SSH (Método fácil: EC2 Instance Connect)

Esta es la forma más rápida, sin instalar nada:

  1. Con la instancia seleccionada, haz clic en el botón Connect (arriba a la derecha).
  2. En la pestaña EC2 Instance Connect, deja todo como está.
  3. Haz clic en el botón naranja Connect.
  4. Se abrirá una terminal negra en tu navegador. ¡Ya estás dentro del servidor!
💡 ¿Prefieres usar PuTTY o Git Bash? Entonces copia la Public IPv4 address de la instancia (aparece en la pestaña "Details" abajo) y conéctate como siempre: ssh -i tu-llave.pem ec2-user@IP-PUBLICA
3

🔥 Ejecutar el comando de estrés

Escribe este comando en la terminal y presiona Enter:

stress --cpu 1 --timeout 600

¿Qué hace? Simula que 1 proceso está usando la CPU al 100% durante 10 minutos (600 segundos). Como el t2.micro tiene solo 1 CPU virtual, esto lo llevará al máximo.

⚠️ ¿Te sale "stress: command not found"? Significa que el User Data aún no terminó de instalar. Ejecuta esto manualmente y luego vuelve a intentar:
sudo yum install stress -y
💡 Plan B si nada funciona: Este comando hace lo mismo sin necesidad de instalar nada:
yes > /dev/null &
(Ejecútalo 2 veces para asegurar saturación. Para detenerlo después: killall yes)
4

Verificar que la CPU está al 100%

Si quieres ver la CPU sufriendo en tiempo real, abre una segunda conexión SSH (repite el paso 2) y ejecuta:

top

Verás algo como %Cpu(s): 99.7 us en la parte superior. Eso significa que la CPU está al 100%. Deja ambas ventanas abiertas y pasa al siguiente paso.

✅ Si todo salió bien: La terminal donde ejecutaste stress debería quedarse "congelada" (eso es normal, está trabajando). No la cierres. Ahora pasa al siguiente paso para ver la magia.

4 ¡Auto Scaling en Acción! 🎯

💡 Guía Docente: El Momento Wow (10-15 min de espera)

Este es el momento cumbre de la clase. CloudWatch con monitoreo básico (el gratuito) toma métricas cada 5 minutos, y la alarma necesita 3 datos consecutivos en breach para disparar. Esto significa una espera real de 5 a 10 minutos. Usa ese tiempo para:

  • Preguntar a los alumnos: "¿Qué creen que va a pasar?", "¿Por qué AWS no reacciona instantáneamente?"
  • Explicar que en producción se usa Detailed Monitoring (métricas cada 1 minuto, de pago) para reaccionar más rápido.
  • Llevarlos a la pestaña Activity del ASG para que vean el log de eventos en vivo.
  • Si después de 12 minutos no aparece nada, verificar la pestaña "Automatic scaling" del ASG y confirmar que la política de Target Tracking está creada.

La trampa está tendida. Tu servidor está agonizando al 100% de CPU. Ahora siéntate y observa cómo la nube reacciona sola.

1

Vuelve a la consola de AWS

Deja la terminal SSH abierta (con el estrés corriendo) y vuelve a tu navegador. Ve a EC2 → Instances.

Ahora mismo deberías ver solo 1 instancia en estado "Running".

2

⏳ Esperar y refrescar (5 a 10 minutos — ten paciencia)

¿Por qué tarda tanto? AWS no reacciona al instante a propósito. CloudWatch con monitoreo básico (gratuito) toma métricas de CPU cada 5 minutos, y necesita ver varios datos consecutivos por encima del umbral antes de disparar la alarma. Esto evita que un pico de 10 segundos cause un escalado innecesario (que costaría dinero).

Mientras esperas:

  • Haz clic en el botón de refrescar (🔄) en la esquina superior derecha de la tabla de instancias cada 30 segundos.
  • Ve a Auto Scaling Groups → MiGrupoAutoScaling → pestaña Activity para ver el log de eventos en vivo. Cuando veas un evento nuevo de tipo "Launching", ¡es que está pasando!
  • También puedes revisar la pestaña Monitoreo de tu instancia para ver cómo sube el gráfico de CPU (tarda unos minutos en actualizarse).
⚠️ Es normal que el gráfico de CPU muestre 30-40% al principio. CloudWatch está promediando datos. Dale unos minutos más y verás cómo sube a 90-100%. La alarma se disparará cuando acumule suficientes lecturas consecutivas por encima del 50%.
3

🎉 ¡APARECE UNA SEGUNDA INSTANCIA!

De pronto verás aparecer una nueva instancia en estado "Pending" que tú nunca lanzaste manualmente.

¿Qué acaba de pasar?

  1. CloudWatch detectó que la CPU promedio del grupo superó el 50%.
  2. Disparó una alarma al Auto Scaling Group.
  3. El ASG consultó tu Launch Template ("la receta").
  4. Creó un servidor idéntico automáticamente para repartir la carga.
🏆 ¡Felicidades, Arquitecto Cloud! Acabas de presenciar la elasticidad de la nube en vivo. Este es exactamente el mecanismo que usan Netflix, Spotify y todas las empresas para sobrevivir a picos de tráfico sin caerse.
🔄 Bonus: El desescalado automático
Si detienes el estrés en la terminal (presiona Ctrl+C), la CPU bajará a 0%. Después de unos minutos, AWS detectará que ya no necesita el servidor extra y lo destruirá automáticamente para que no pagues de más. ¡Eso es el "Scale In"!

5 Limpieza de Recursos ⚠️

💡 Guía Docente: Limpieza (5 min)

CRÍTICO: No dejes que los alumnos se vayan sin eliminar el ASG. Si el ASG sigue activo, seguirá creando instancias y consumiendo créditos. El orden importa: primero el ASG, luego la plantilla.

🚨 OBLIGATORIO: Debes eliminar estos recursos AHORA. Si dejas el Auto Scaling Group corriendo, seguirá creando instancias y gastando tus créditos de AWS Academy incluso cuando no estés conectado.

Sigue este orden exacto (el orden importa):

1

Eliminar el Auto Scaling Group

  1. Ve a EC2 → Auto Scaling Groups (menú izquierdo, abajo del todo).
  2. Selecciona MiGrupoAutoScaling (checkbox).
  3. Haz clic en el botón Delete (arriba).
  4. Te pedirá confirmación: escribe delete y confirma.

Esto automáticamente terminará todas las instancias que el grupo haya creado.

2

Verificar que no quedan instancias

  • Ve a EC2 → Instances.
  • Espera 1-2 minutos y refresca. Todas las instancias del grupo deberían pasar a estado "Terminated" (texto gris).
  • Si alguna sigue en "Running", selecciónala y haz clic en Instance state → Terminate instance.
3

Eliminar la Launch Template

  • Ve a EC2 → Launch Templates.
  • Selecciona MiPlantillaRescate.
  • Haz clic en Actions → Delete template.
  • Escribe Delete para confirmar.
✅ Limpieza completa: Si no ves ninguna instancia en "Running" y no tienes Auto Scaling Groups activos, estás limpio. No se te cobrará nada adicional.

📝 ¿Qué Aprendí Hoy?

Responde estas preguntas para verificar que entendiste los conceptos fundamentales del Auto Scaling.

1. ¿Para qué sirve una Launch Template?

Es la "receta" que le dice a AWS exactamente cómo crear un servidor (qué sistema operativo, qué tamaño, qué scripts ejecutar). Así puede clonarlos de forma idéntica.
Es un servidor que ya está corriendo y que AWS copia a mano cuando le pides más capacidad.
Es un documento PDF que describes las especificaciones técnicas del servidor para que el equipo de soporte lo revise.

2. ¿Qué métrica usamos para que el Auto Scaling decidiera cuándo crear más servidores?

El uso de disco duro (almacenamiento).
El uso promedio de CPU (Average CPU utilization). Configuramos el umbral en 50%.
La cantidad de archivos en el servidor.

3. ¿Qué pasaría si configuras bien el "Scale Out" (escalar arriba) pero olvidas el "Scale In" (desescalar)?

No pasaría nada, AWS se encarga de todo automáticamente sin importar la configuración.
Los servidores se apagarían solos después de 24 horas.
Los servidores extra se quedarían corriendo para siempre, y la factura de AWS crecería sin control hasta que alguien los apague manualmente.
